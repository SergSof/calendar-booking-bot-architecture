# Архитектура бота для записи на встречи через Google Calendar

Тестовое задание: спроектировать архитектуру бота, через которого организатор подключает свой Google Calendar, а гости могут видеть свободные слоты и записываться на встречу без доступа к самому календарю организатора.

## Что решает система

Система должна позволять:

- авторизовать организатора через Google OAuth 2.0;
- безопасно хранить и обновлять OAuth-токены;
- показывать гостям только свободные слоты без раскрытия деталей календаря;
- бронировать слот и создавать событие в Google Calendar;
- защищаться от двойного бронирования одного слота;
- отменять встречу и уведомлять обе стороны.

## Выбранная платформа

В качестве платформы выбран Telegram-бот.

Причины выбора:

- быстрый и понятный интерфейс для организатора и гостей;
- удобно реализовать выбор слотов через inline-кнопки;
- подтверждения, отмены и уведомления можно отправлять прямо в чат;
- Telegram хорошо подходит для MVP и демонстрации архитектуры.

## Основная идея архитектуры

Гость не получает прямой доступ к календарю организатора.

Вся работа с Google Calendar происходит через backend:

1. Организатор авторизуется через Google OAuth 2.0.
2. Backend сохраняет OAuth-токены в базе данных.
3. Организатор задаёт правила доступности.
4. Гость запрашивает свободные слоты через Telegram-бота.
5. Backend получает занятость из Google Calendar API.
6. Система показывает гостю только свободные интервалы.
7. После выбора слота backend создаёт событие в календаре организатора.

Детали чужих событий, названия встреч, участники и личная информация из календаря гостю не раскрываются.

## Основные компоненты

- **Telegram Bot** — интерфейс для организатора и гостей.
- **Backend / Bot Service** — основная бизнес-логика: OAuth, генерация слотов, бронирование, отмена.
- **PostgreSQL** — хранение пользователей, организаторов, правил доступности, бронирований и OAuth-токенов.
- **Google Calendar API** — получение занятости календаря, создание и отмена событий.
- **DB transactions / unique constraints** — защита от двойного бронирования.
- **n8n** — опциональный вспомогательный слой для уведомлений и фоновых задач, не основной механизм бронирования.

## Допущения

В задании не указано, как именно организатор задаёт доступные слоты.

Я принял допущение, что организатор задаёт правила доступности внутри бота:

- дни недели;
- временные окна;
- длительность встречи;
- буфер между встречами.

Пример:

```text
Пн–Пт, 10:00–18:00
Длительность встречи: 30 минут
Буфер между встречами: 10 минут
```

Система на основе этих правил и занятости из Google Calendar показывает гостю только реально свободные слоты.

## Что не входит в решение

Это архитектурное тестовое задание, а не полноценная production-реализация.

В рамках решения не реализуются:

* реальный backend;
* реальный Telegram-бот;
* реальный OAuth-клиент Google;
* деплой;
* админ-панель;
* платежи;
* сложная система напоминаний;
* поддержка нескольких календарей на одного организатора.

Эти части можно добавить позже, если архитектурный прототип будет развиваться в полноценный продукт.
