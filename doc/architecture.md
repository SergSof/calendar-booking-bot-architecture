
# Архитектурное решение: бот для записи на встречи через Google Calendar

## Что я понял о задаче

Нужно спроектировать архитектуру бота для записи на встречи через Google Calendar.

Есть две основные роли: организатор и гость. Организатор подключает свой Google Calendar через OAuth 2.0 и задаёт правила доступности. Гость не получает доступ к календарю организатора, а видит только свободные слоты и может выбрать удобное время для встречи.

Ключевые требования архитектуры: безопасно хранить OAuth-токены, не раскрывать гостю детали чужих событий, корректно создавать событие в Google Calendar, защититься от двойного бронирования одного слота и поддержать отмену встречи с уведомлением обеих сторон.

В задании не указано, как именно организатор задаёт доступные слоты, поэтому я принял допущение: организатор задаёт правила доступности внутри бота — дни недели, временные окна, длительность встречи и буфер между встречами.

## Архитектурная схема

Основные компоненты системы:

- **Telegram Bot** — интерфейс для организатора и гостей.
- **Backend / Bot Service** — основная бизнес-логика: OAuth, генерация слотов, бронирование, отмена.
- **PostgreSQL** — хранение пользователей, организаторов, правил доступности, бронирований и OAuth-токенов.
- **Google Calendar API** — получение занятости календаря, создание и отмена событий.
- **Notification layer** — отправка подтверждений и уведомлений через Telegram.
- **n8n** — опциональный вспомогательный слой для уведомлений, напоминаний или простых фоновых задач. Основную логику бронирования я бы не выносил в n8n.

Упрощённая схема:

```text
Гость / Организатор
        |
        v
 Telegram Bot
        |
        v
 Backend / Bot Service
        |
        +--------------------+
        |                    |
        v                    v
 PostgreSQL          Google Calendar API
        |
        v
 Данные системы:
 пользователи,
 организаторы,
 правила доступности,
 OAuth-токены,
 бронирования,
 события календаря
````

### Где живут данные

В PostgreSQL хранятся:

* пользователи Telegram;
* организаторы;
* правила доступности организатора;
* OAuth-токены Google;
* бронирования;
* связь бронирования с событием в Google Calendar;
* статусы встреч: `pending`, `confirmed`, `cancelled`.

Пример основных таблиц:

```text
users
- id
- telegram_id
- role
- created_at

organizers
- id
- user_id
- google_account_email
- timezone
- created_at

oauth_tokens
- id
- organizer_id
- access_token_encrypted
- refresh_token_encrypted
- expires_at
- scopes
- created_at
- updated_at

availability_rules
- id
- organizer_id
- weekday
- start_time
- end_time
- slot_duration_minutes
- buffer_minutes
- is_active

bookings
- id
- organizer_id
- guest_user_id
- start_at
- end_at
- status
- google_event_id
- created_at
- cancelled_at
```

## OAuth-флоу организатора

Цель OAuth-флоу — дать backend доступ к календарю организатора без передачи логина и пароля.

### Шаги

1. Организатор открывает Telegram-бота и выбирает действие:
   **Подключить Google Calendar**.

2. Backend создаёт OAuth-ссылку Google и добавляет в неё:

   * `client_id`;
   * `redirect_uri`;
   * необходимые scopes;
   * `state` для защиты от CSRF и связи запроса с конкретным организатором;
   * параметр для получения refresh token.

3. Организатор переходит по ссылке и авторизуется в Google.

4. Google возвращает пользователя на backend callback URL:

```text
GET /oauth/google/callback?code=...&state=...
```

5. Backend проверяет `state`.

6. Backend обменивает `code` на:

   * `access_token`;
   * `refresh_token`;
   * `expires_at`;
   * список выданных scopes.

7. Refresh token сохраняется в базе данных в зашифрованном виде.

8. Access token используется для запросов к Google Calendar API.

9. Когда access token истекает, backend обновляет его через refresh token.

### Где хранится токен

Токены хранятся в таблице `oauth_tokens`.

Refresh token нельзя хранить в открытом виде. Его нужно шифровать на уровне приложения перед записью в базу.

Пример:

```text
refresh_token -> encryption -> encrypted_refresh_token -> PostgreSQL
```

Ключ шифрования хранится не в базе, а в переменных окружения или secret manager.

### Какие scopes нужны

Минимально нужны права на работу с календарём организатора.

Я бы не запрашивал слишком широкие права без необходимости. Лучше использовать минимальный набор scopes, достаточный для:

* проверки занятости календаря;
* создания события;
* отмены или удаления созданного события.

## Флоу бронирования гостем

Гость не видит календарь организатора напрямую. Он работает только с ботом.

### Шаги

1. Гость открывает Telegram-бота.

2. Гость выбирает организатора или переходит по специальной ссылке на запись:

```text
https://t.me/bot_name?start=organizer_123
```

3. Backend определяет организатора.

4. Backend загружает из базы правила доступности организатора:

```text
Пн–Пт
10:00–18:00
Длительность встречи: 30 минут
Буфер: 10 минут
```

5. Backend запрашивает занятость календаря через Google Calendar API.

6. Backend строит список потенциальных слотов по правилам доступности.

7. Backend исключает занятые интервалы из Google Calendar.

8. Backend дополнительно исключает уже забронированные слоты из таблицы `bookings`.

9. Гость видит только свободные слоты, например:

```text
Сегодня:
12:00
12:30
15:00
16:30
```

10. Гость выбирает слот.

11. Backend пытается создать бронирование в базе.

12. Если бронирование успешно создано, backend создаёт событие в Google Calendar.

13. Google возвращает `event_id`.

14. Backend сохраняет `google_event_id` в бронировании.

15. Бот отправляет подтверждение гостю и организатору.

### Что видит гость

Гость видит только свободное время.

Он не видит:

* названия событий организатора;
* участников других встреч;
* описания событий;
* личную информацию из календаря;
* причину занятости конкретного времени.

## Как защищаемся от двойного бронирования

Главная проблема: два гостя могут почти одновременно выбрать один и тот же слот.

Например:

```text
Гость A выбирает 15:00
Гость B выбирает 15:00
```

Если проверять слот только на уровне Telegram-бота или n8n workflow, можно получить race condition: оба пользователя увидели слот свободным и оба пытаются его занять.

Поэтому защита должна быть на уровне базы данных.

### Решение

Использовать:

1. транзакцию в PostgreSQL;
2. уникальное ограничение на слот;
3. повторную проверку занятости перед созданием события в Google Calendar.

Пример уникального ограничения:

```sql
CREATE UNIQUE INDEX unique_active_booking_slot
ON bookings (organizer_id, start_at, end_at)
WHERE status IN ('pending', 'confirmed');
```

### Логика бронирования

1. Гость выбирает слот.
2. Backend открывает транзакцию.
3. Backend пытается вставить запись в `bookings` со статусом `pending`.
4. Если запись вставилась — слот временно занят.
5. Если база вернула ошибку уникальности — слот уже занят.
6. Backend создаёт событие в Google Calendar.
7. Если событие создано успешно — бронирование переводится в `confirmed`.
8. Если Google Calendar API вернул ошибку — бронирование отменяется или помечается как `failed`.

### Почему именно так

Потому что Telegram Bot, n8n или frontend-кнопки не могут гарантировать защиту от одновременных действий пользователей.

Гарантия должна быть на уровне общего источника истины — базы данных.

PostgreSQL транзакция и уникальный индекс дают понятное и надёжное поведение: один слот может быть забронирован только один раз.

## Отмена и уведомления

Отмена может быть инициирована гостем или организатором.

### Отмена гостем

1. Гость нажимает кнопку отмены в Telegram.
2. Backend находит активное бронирование.
3. Backend меняет статус бронирования на `cancelled`.
4. Backend удаляет или отменяет событие в Google Calendar по `google_event_id`.
5. Бот уведомляет организатора.
6. Бот подтверждает гостю отмену.

### Отмена организатором

1. Организатор выбирает встречу в боте.
2. Организатор нажимает отмену.
3. Backend меняет статус бронирования на `cancelled`.
4. Backend отменяет событие в Google Calendar.
5. Бот уведомляет гостя.
6. Бот подтверждает организатору отмену.

### Уведомления

Минимально нужны уведомления:

* гостю после успешной записи;
* организатору после новой записи;
* обеим сторонам при отмене;
* гостю, если выбранный слот уже занят;
* организатору, если Google Calendar был отключён или токен стал невалидным.

## 3 сценария: вход → действие системы → почему

### Сценарий 1: гость выбирает слот, который только что занял другой пользователь

**Вход:**
Гость A и Гость B одновременно выбирают слот на 15:00.

**Действие системы:**
Backend пытается создать бронирование в PostgreSQL. Для одного пользователя вставка проходит успешно. Для второго база возвращает ошибку уникального ограничения.

**Почему:**
Защита от двойного бронирования реализована на уровне базы данных, а не только на уровне интерфейса. Это защищает систему от race condition.

---

### Сценарий 2: у организатора истёк access token Google

**Вход:**
Гость запрашивает свободные слоты, но access token организатора уже истёк.

**Действие системы:**
Backend использует refresh token, получает новый access token, сохраняет обновлённые данные и повторяет запрос к Google Calendar API.

**Почему:**
Access token имеет ограниченное время жизни. Refresh token нужен, чтобы организатору не приходилось заново подключать календарь при каждом истечении access token.

---

### Сценарий 3: гость открыл старую кнопку со слотом

**Вход:**
Гость открыл старое сообщение в Telegram и нажал кнопку со слотом, который уже недоступен.

**Действие системы:**
Backend не доверяет данным из кнопки и заново проверяет слот: смотрит бронирования в базе и занятость в Google Calendar. Если слот уже занят, бот сообщает гостю, что время больше недоступно, и предлагает выбрать другой слот.

**Почему:**
Inline-кнопки в Telegram могут устаревать. Нельзя считать слот свободным только потому, что кнопка была показана пользователю раньше.

## Что я бы НЕ стал делать и почему

Я бы не стал строить архитектуру так, чтобы гость напрямую получал доступ к Google Calendar организатора.

На первый взгляд это могло бы упростить задачу: гость сам смотрит календарь и выбирает свободное время. Но это неправильное решение по нескольким причинам:

1. Гость может увидеть личные события организатора.
2. Сложнее контролировать, какие данные раскрываются.
3. Появляются лишние риски безопасности.
4. Сложнее управлять правами доступа.
5. Это противоречит задаче: гость должен видеть только свободные слоты, а не сам календарь.

Также я бы не стал делать n8n основным механизмом бронирования.

n8n можно использовать для уведомлений, напоминаний и простых интеграционных задач. Но критичную часть — создание брони, проверку уникальности и защиту от двойного бронирования — лучше держать в backend и PostgreSQL.

## Что требует уточнения

Перед финализацией архитектуры я бы уточнил у команды следующие вопросы.

### 1. Как организатор должен задавать доступные слоты?

Варианты:

* вручную создавать отдельные слоты;
* задавать регулярное расписание;
* использовать рабочие часы из Google Calendar;
* комбинировать правила доступности и текущую занятость календаря.

В моём решении принято допущение, что организатор задаёт правила доступности внутри бота.

---

### 2. Нужны ли разные типы встреч?

Например:

* 15 минут;
* 30 минут;
* 60 минут;
* консультация;
* интервью;
* демо-звонок.

Если типы встреч нужны, то длительность и буфер должны зависеть от типа встречи.

---

### 3. Нужны ли напоминания?

Например:

* за 24 часа;
* за 1 час;
* за 10 минут.

Если напоминания нужны, можно реализовать их через backend scheduler, очередь задач или n8n.

---

### 4. Может ли один организатор подключить несколько календарей?

Например:

* основной календарь;
* рабочий календарь;
* календарь команды.

Если да, нужно хранить список календарей и понимать, в какой календарь создавать событие.

---

### 5. Что делать, если событие было изменено напрямую в Google Calendar?

Например, организатор удалил или перенёс встречу не через бота, а вручную в Google Calendar.

Возможные решения:

* периодическая синхронизация;
* Google Calendar push notifications;
* проверка статуса события перед показом или отменой.

---

### 6. Нужна ли авторизация гостей?

В минимальном варианте гость определяется по Telegram ID.

Но если нужно больше данных, можно запрашивать:

* имя;
* телефон;
* email;
* комментарий к встрече.

---

### 7. Нужна ли поддержка часовых поясов?

Если гости и организатор могут быть в разных странах, нужно явно показывать часовой пояс слота.

Например:

```text
15:00 Asia/Bangkok
11:00 Europe/Moscow
```

---

### 8. Что должно происходить при ошибке Google Calendar API?

Например:

* токен отозван;
* календарь недоступен;
* превышены лимиты API;
* событие не создалось после успешной записи в базе.

Для таких случаев нужен понятный fallback: отменить бронь, показать ошибку гостю и уведомить организатора.

---

## Итоговое решение

Я предлагаю архитектуру, где Telegram используется как пользовательский интерфейс, backend отвечает за бизнес-логику, PostgreSQL является источником истины для бронирований, а Google Calendar API используется для проверки занятости и создания событий.

Основная защита от двойного бронирования реализована через транзакции и уникальные ограничения в PostgreSQL.

Гость не получает доступ к календарю организатора и видит только свободные слоты. Детали событий, участники и личные данные из календаря не раскрываются.

n8n можно использовать как вспомогательный инструмент для уведомлений или напоминаний, но не как основной механизм бронирования.
